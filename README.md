# DERMAI

Application web d'analyse cosmétique de la peau et de routine personnalisée (français, mobile d'abord, responsive bureau). Un mode démonstration à données fictives existe à part.

Fichiers : `index.html`, `css/styles.css`, `js/app.js`. Ouvre `index.html` dans un navigateur, aucune installation.

## Écrans
Accueil, inscription, onboarding, scan (une photo de face ; trois en mode démonstration), analyse, résultats, détail par préoccupation,
actifs, routine matin/soir, produits, progression, historique des analyses, profil, confidentialité.

## Données d'analyse
Dans `js/app.js` : `DEMO_MODE = true` : données et photo fictives (`MockProvider`).
Mettre `false` pour appeler `POST /api/skin-analysis` (`PerfectCorpProvider`).
Ce backend n'existe pas encore : il doit garder la clé API et renvoyer le JSON brut du fournisseur.
Une valeur absente reste `null` et l'indicateur est masqué, jamais inventé.

## Configuration par environnement (Vercel)
- `DERMAI_DEMO_MODE` : vide ou absente = mode démo (défaut, Production). `false` (ou `0`, `no`, `off`) = le frontend appelle le backend.
  À définir uniquement sur l'environnement Preview de test. Le frontend lit cette valeur via `/api/config-js` (fonction `api/config-js.js`), chargé par `index.html` avant `app.js`.
- `DERMAI_ANALYSIS_ENABLED` : verrou de `/api/skin-analysis`, fermé par défaut.
- `PERFECT_CORP_API_KEY` : clé Perfect Corp, côté serveur uniquement.
- `DERMAI_DEBUG_RAW` : diagnostic, renvoie le JSON brut au navigateur. Laisser vide.
- `SUPABASE_URL` et `SUPABASE_ANON_KEY` : comptes et profil persistant (Supabase Auth). Valeurs PUBLIQUES, exposées au navigateur par `/api/config-js` (URL du projet en `https://…` et clé « anon »).
  Sans elles (ou en mode démo), les comptes sont simplement indisponibles. Ne jamais définir la clé `service_role` dans le frontend ni dans `/api/config-js`.

## Comptes et profil (Supabase)
- Authentification : e-mail + mot de passe (Supabase Auth). Aucun mot de passe n'est stocké par DERMAI ; seule la session d'authentification est mémorisée dans le navigateur (clé `dermai.session`).
- Profil : table `public.profiles` (objectifs, niveau de routine, approche douce, exclusions). Migration : `supabase/migrations/20261006120000_create_profiles.sql`
  (à appliquer avec `supabase db push` ou en l'exécutant dans l'éditeur SQL du projet). RLS activée : chaque utilisateur ne lit et ne modifie que sa propre ligne ; `user_id` vient de `auth.uid()`.
- Historique : table `public.skin_analyses` (une ligne par analyse réelle réussie d'un utilisateur connecté). Migration : `supabase/migrations/20261007120000_create_skin_analyses.sql`
  (à appliquer **avant** de promouvoir cette version en production, comme la précédente). Elle conserve ce que DERMAI a mesuré et recommandé à la date de l'analyse : score global, type de peau, âge cutané,
  les 15 `uiScore` (entiers 0-100, 100 = meilleur ; `null` = indisponible), priorités (id, libellé, score, bande), objectifs du moment, version des règles (`engine_version`, `Engine.VERSION`).
  Une analyse enregistrée est figée (aucune modification possible côté client) et n'est jamais recalculée. RLS : lecture, ajout et suppression de ses propres lignes seulement.
  Pas d'enregistrement en mode démo, pour un visiteur non connecté, ni pour une analyse échouée.
- Analyse : `POST /api/skin-analysis` exige une session Supabase valide (`Authorization: Bearer <access_token>`). Le serveur vérifie le jeton auprès de Supabase (`GET /auth/v1/user`, clé publique `SUPABASE_URL` / `SUPABASE_ANON_KEY`, aucune clé `service_role`) AVANT de lire la photo et d'appeler Perfect Corp ; ordre : méthode, authentification, verrou `DERMAI_ANALYSIS_ENABLED`, validation de la photo, Perfect Corp. Sans session, jeton invalide, expiré, falsifié, ou Supabase injoignable : refus (401 / 503), aucune unité consommée. Un visiteur peut naviguer ; lancer une analyse l'oriente vers la connexion.
- Quota d'analyses : la base réserve chaque analyse avant l'appel à Perfect Corp (`reserve_analysis`, migration `20261008120000_analysis_quota.sql`, atomique par utilisateur, indépendant de l'historique). Réglable par variables Vercel : `DERMAI_MAX_ANALYSES_PER_PERIOD` (défaut 3) et `DERMAI_ANALYSIS_PERIOD_HOURS` (défaut 24). Tout ce qui atteint l'étape fournisseur compte, même en échec ; photo invalide, non connecté ou verrou fermé ne comptent pas. Si la fonction est absente ou la base injoignable, l'analyse est refusée (503).
- **Lien magique** (connexion par e-mail, sans mot de passe ; `js/quick-login.js`, mise en place dans `docs/quick-login.md`) : « Recevoir un lien de connexion par e-mail » sous le formulaire de connexion et d'inscription. L'adresse saisie reçoit un lien ; l'ouvrir connecte la personne (compte créé au premier passage, même réponse que l'adresse existe ou non). La session revient dans l'adresse du site, est lue par le code existant de retour de lien, vérifiée auprès de Supabase puis effacée de l'adresse. Connexion Google et Apple : abandonnées.
- **Œil « afficher / masquer le mot de passe »** dans chaque champ de mot de passe (connexion, inscription, nouveau mot de passe) : `js/password-toggle.js` + `css/components/form.css`, sans modifier `js/app.js`. Masqué par défaut, remasqué quand la page passe en arrière-plan, le champ garde le focus, bouton accessible au clavier (`aria-label`, `aria-pressed`). Le module ne lit, ne copie et ne garde aucune valeur.

## Pays d'achat et options d'achat (étape 15)

DERMAI est pensé pour toute l'Afrique : aucun pays par défaut, aucune offre déduite d'un pays à l'autre.

- **Pays choisi volontairement** : section « Pays pour mes achats » dans le profil, et invitation « Où souhaitez-vous acheter vos produits ? » sur la page Produits tant qu'aucun pays n'est choisi. Aucune géolocalisation, aucune adresse IP, aucun blocage : on peut analyser et consulter sa routine sans choisir de pays.
- **Liste centralisée** : `js/engine/data/markets.js` (54 pays : code ISO, nom français, nom anglais, article, devise principale). Étendre = une ligne. `js/market.js` : préférence (lecture, écriture, liste du sélecteur, « pour le Bénin »).
- **Stockage** : uniquement dans le navigateur (`localStorage`, clé `dermai.market`). Ce n'est pas une donnée d'analyse ni de personnalisation : il n'est ni dans le profil Supabase, ni dans une analyse (`goals_snapshot`), ni envoyé à Perfect Corp. Aucune table, aucune colonne, aucune migration. Conséquence : le choix suit l'appareil, pas le compte. Un stockage refusé par le navigateur ne casse rien (le choix vaut pour la visite).
- **Moteur souverain** : le pays n'est lu que par l'affichage des offres (`marketView` dans `js/engine/products.js`, page Produits, fiche). Il ne change ni le score, ni les priorités, ni les actifs, ni la routine, ni le classement « Recommandés » / « Autres produits » (tests MK12, MK13).
- **Hiérarchie des offres** : 1. offres du pays (« Vendeur local ») ; 2. offres régionales, seulement si le vendeur déclare desservir ce pays (`servesMarkets`) ; 3. offres d'autres pays (« Voir une offre internationale » (carte) / « Offre internationale » (ligne d'offre), repliées, « Vérifier la livraison lors de la commande ») ; 4. « Aucune offre vérifiée pour ce pays pour le moment. ». Une offre dont le vendeur indique une livraison locale n'est jamais proposée hors de son pays. Aucun score, aucun classement numérique.
- **Prix et devises** : chaque prix reste dans la devise de son offre (jamais converti en FCFA), « Prix relevé » + date de relevé ; sans prix : « Prix à vérifier ». Disponibilité : En stock, Rupture de stock, Bientôt disponible, Disponibilité à vérifier (`unknown` n'est jamais « Disponible »).
- **Bouton « Acheter en ligne »** : seulement avec un lien https réel, un vendeur identifié et une offre en stock ; sur une carte, seulement pour un produit retenu par la routine. Aucun lien généré, aucune affiliation, aucun suivi.
- **Mode démonstration** : aucun sélecteur de pays, aucune offre réelle, produits marqués « Démo ».

## Qualité des offres (affichage seulement)

Chaîne : actif retenu → produits compatibles → exclusions / approche douce → **choix du produit (moteur, inchangé)** → offres du pays sélectionné → qualité de l'offre. Le pays et la qualité n'agissent qu'après le choix du produit : ils ne font jamais passer un produit de « Autres produits » à « Recommandés » (test Q4 : mêmes sections pour les 54 pays et avec ou sans offres).

- `qualityOf` (dans `products.js`) classe grossièrement chaque offre : `ready` (stock indiqué, prix et lien https), `partial` (stock inconnu, prix ou lien absent), `unavailable` (rupture, bientôt disponible). Ce n'est ni un score ni un pourcentage. Dans un même niveau (pays, régional, autres pays), les offres sont présentées dans cet ordre.
- `marketView(...).summary` résume le pays : « Offre locale : stock et prix indiqués au relevé », « Offre locale à vérifier : stock, prix ou lien non confirmé », « Offre locale : rupture ou bientôt disponible », « Offres dans d'autres pays seulement », « Aucune offre vérifiée pour ce pays pour le moment. » (affiché sur la fiche produit).
- Le bouton « Acheter en ligne » n'existe que pour une offre `ready`.

## Audit de séparation moteur / catalogue / marché (étape 18)

`test/separation-audit.test.js` verrouille la frontière : le **moteur** décide (actifs, routine, produits retenus), le **catalogue** décrit les produits, le **marché** (pays, offres, qualité) n'arrive qu'après et ne sert qu'à l'affichage. Seule correction : le bouton « Acheter en ligne » est maintenant strictement réservé à une offre `ready` (avant, une offre en stock sans prix pouvait l'afficher alors qu'elle est `partial`).

## Départage entre produits d'un même actif (étape 19)

Lorsqu'un actif possède plusieurs produits compatibles, DERMAI utilise une priorité éditoriale explicite (`editorialPriority: { actif: rang }`, 1 = d'abord, facultative). À priorité égale ou en l'absence de priorité, l'ordre du catalogue sert de repli. Ce choix est indépendant du marché et des offres commerciales. Ordre complet dans `match()` : actifs recherchés présents, type de peau, priorité éditoriale, ordre du catalogue ; les exclusions, l'approche douce et la composition filtrent avant et ne sont jamais contournées. Un produit sans priorité explicite passe après ceux qui en ont une (aucune valeur n'est inventée). La priorité ne s'applique qu'aux étapes de traitement et n'est jamais affichée.

Priorités actuelles (ordre éditorial en vigueur, sans jugement de valeur) : vitamin_c : The Ordinary Ascorbyl Glucoside 12 % (1), CeraVe Skin Renewing Vitamin C Serum (2) ; salicylic : The Ordinary Salicylic Acid 2 % (1), La Roche-Posay Pure Vitamin C10 (2). Aucun autre actif n'a de hiérarchie : un seul produit y concourt.

## Zones détectées sur la photo (étape 21B)

- **Source unique : les masques de Perfect Corp.** Chaque métrique de `data.results.output` peut porter un tableau `mask_urls` (URL temporaires chez le fournisseur). `server/masks.js` lit ces URL sur les 15 métriques connues seulement, les télécharge côté serveur (https uniquement, sans clé API, taille et délai limités, type vérifié sur les octets), et les renvoie dans la réponse de l'analyse sous la clé `localization` : `{ <clé DERMAI>: [data URL, …] }`. Les URL d'origine ne quittent jamais le serveur. Plusieurs masques pour une même métrique sont conservés, dans l'ordre. Aucun masque exploitable → clé absente. Un échec de téléchargement ne fait jamais échouer l'analyse.
- **Aucune zone inventée.** Ni le score, ni les priorités, ni le type de peau, ni le pays ne servent à dessiner quoi que ce soit (`js/face-map.js` ne les connaît pas). Le score indique une intensité ; le masque, une localisation.

Les masques sont dessinés dans la même boîte que la photo. Le masque n'est superposé que s'il a les mêmes proportions que la photo (tolérance 1 %) et qu'il est lisible : fond transparent, ou niveaux de gris sur fond sombre. Sinon rien n'est dessiné et un message discret s'affiche (« Localisation visuelle indisponible pour cet indicateur. »). Couleur et opacité fixes (rose-corail DERMAI), jamais liées au score. Étiquette : nom de l'indicateur et vrai `ui_score`.

L'interprétation en tient compte depuis l'étape 26.3 (section dédiée plus bas). Les tests (`test/face-map.test.js`, `test/real-masks.test.js`) utilisent des masques générés qui reproduisent ces mesures.

## Masques semi-transparents (étape 26.3)

Constat (mesure sur 15 vrais masques) : l'alpha est continu et reste presque toujours sous 128. L'ancien seuil `alpha >= 128` déclarait vides des masques qui contenaient de vraies zones (rougeurs, brillance, pores, pigmentation, poches…) et affichait à tort « indisponible ». Correction limitée à `js/face-map.js` ; moteur, scores, seuils 50 / 25, priorités, routine et produits inchangés (empreinte C0).

- **Plancher de bruit** : alpha < 16 (fond transparent) ou luminance < 31 (fond sombre), les mêmes valeurs que la détection du fond. Rien en dessous n'est compté ni dessiné.
- **Couverture effective** : `coverage = Σ alpha / (255 × nombre de pixels)`, une moyenne pondérée par l'alpha. Information technique seulement : jamais lue par une décision.
- **Vide** : moins de pixels présents (≥ plancher) que l'aire d'un pixel d'écran à la plus grande largeur de la carte, soit `max(1, (largeur du masque / 560)²)`. Le seuil suit la taille du masque, ce n'est pas un nombre fixe.
- **Niveau technique** : `empty`, `faint` (pic < 128) ou `visible`. C'est un niveau de rendu, pas une gravité : DERMAI n'attribue aucun sens Perfect Corp à l'alpha faible.
- **Rendu** : le remplissage suit l'alpha du masque rapporté à son propre pic (`FILL × alpha / pic`), donc une zone faible reste lisible et un masque opaque s'affiche comme avant. Le liseré est calculé à la moitié du pic du masque, plus à 128 : une zone faible a aussi son bord. Couleur et opacités fixes.
- **Messages** : pas de masque ou masque illisible → « Localisation visuelle indisponible pour cet indicateur. » ; masque lisible mais vide → « Aucune zone localisée pour cet indicateur sur cette photo. » ; zone faible → affichée, jamais « indisponible ».

## Accompagnement des indicateurs « good » (étape 27, règles `1.3.0`)

Avant : `priorities.items` était à la fois le classement des priorités, la liste des axes, le déclencheur des actifs, de la routine et des produits. Un raw à 49,9 donnait un soin, un raw à 50 plus rien. Maintenant : une **deuxième voie**, calculée après les priorités, qui ne les modifie pas (mêmes repères 50 / 25, même ordre, même plafond de 3).

Quatre niveaux, jamais confondus (sorties de `Engine.run` : `priorityItems`, `accompanimentItems`, `accompaniment.recommendations`, `activePlan.treatments[].origin`) :
1. **Priorités** (LOW/MID) : inchangées.
2. **Axe d'accompagnement** (`js/engine/accompaniment.js`) : un indicateur éligible (disponible, rôle `actionable`, ou `goal_gated` avec son objectif ; hors priorités ; avec un actif doux validé non exclu) devient un axe si UNE condition est vraie : **débordement** (candidat LOW/MID écarté par le plafond de 3), **objectif** choisi, ou **distinct** : `valeur < médiane − TIE_TOLERANCE`, strictement (médiane des valeurs de décision des dix indicateurs de comparaison, moyenne des deux valeurs centrales si pair ; médiane 77 : 75 n'est pas distinct, 74,9 l'est). Ordre : débordements, objectifs, distincts, puis valeur croissante (`stableByValue`). Au plus `MAX_ACCOMPANIMENT_AXES` = 2.
3. **Recommandation** : l'actif doux de l'axe (aujourd'hui la niacinamide, seul actif validé, soin ciblé, d'irritation basse) et l'état du produit : `matched`, `no_catalog_product` (actif recommandé, étape présente, aucun produit au catalogue : dit explicitement), `not_applicable` (axe identifié sans étape).
4. **Soin ajouté** (`actives.addAccompaniment`) : une étape (`MAX_ACCOMPANIMENT_STEPS` = 1, origine `accompaniment`) seulement si aucun soin du plan ne cible déjà l'indicateur (sinon l'accompagnement est « couvert », gratuit, sans étape), s'il reste de la place sous le plafond de soins du niveau de routine (inchangé : 1 / 2 / 3), ET s'il y a un **objectif correspondant** OU une **convergence** (`ACCOMPANIMENT_CONVERGENCE` = 2 axes distincts qui partagent réellement le même actif). Un axe identifié n'est donc pas un soin automatiquement ajouté.

Garde-fous inchangés : pool doux = sous-ensemble strict du pool existant (jamais un actif `moderate` ni `à_valider`, jamais de rétinoïde), exclusions, mode confort, un exfoliant fort par soir, plafonds de routine. Jamais lus : masque de localisation, pays, offres, prix, type de peau comme déclencheur, score global, âge cutané (tests C7 et ACC12, ACC28). Constantes : uniquement dans `js/engine/data/decision.js`.

Source unique des rôles : `js/engine/data/decision.js` (`ROLES`, `isInformative`, `isComparable`, `allowsAccompaniment`). `indicators.js` ne définit plus d'« actionnabilité » (le champ `actionability` de l'interprétation est un alias dérivé du rôle).

Limites connues : un seul actif doux validé (rides, fermeté, radiance, contour des yeux n'ont aucun accompagnement possible) ; la règle « distinct » est relative (par rapport aux autres résultats de la même analyse), non calibrée sur des données réelles ; objectifs « texture », « huile » et « fermeté » toujours sans effet sur leur propre indicateur (descriptifs). Les analyses sans raw suivent les mêmes règles sur la base ui (repères 61 / 31). Rien n'est enregistré en plus (pas de migration) : l'historique affiche les priorités enregistrées.

**Empreintes C0** (preuves de non-régression) : `test/c0-priorities.test.js` fige les priorités (ne change jamais) ; `test/analysis-coherence.test.js` : C0 ADDITIF retrouve l'ancienne empreinte des décisions (`4c56df43…`) quand l'accompagnement est désactivé (`MAX_ACCOMPANIMENT_AXES = 0`), C0 COMPLET est la nouvelle empreinte avec accompagnement ; `test/ux-final.test.js` (UX7) retrouve `78d30684…` désactivé. ## Vérif'Routine (v1, saisie manuelle)
Écran `verif` (entrée « Vérif'Routine » de la barre latérale) : l'utilisateur enregistre les produits de sa routine, vérifie leurs ingrédients et consulte des points d'attention fondés **uniquement** sur les données et règles de DERMAI.
- **Fichiers** : `js/engine/verif.js` (analyse pure : découpe INCI, reconnaissance, règles, fréquences), `js/engine/data/inci-aliases.js` (alias justifiés, avec provenance), `js/verif-routine.js` (écrans et stockage), `css/components/verif.css`. `js/app.js` : création du module, route `V.verif`, effacement avec le compte.
- **Ajout d'un produit** : recherche dans le catalogue vérifié (`catalog.js` : produits actifs et validés qui ont une liste INCI relevée sur la fiche du fabricant, avec source et date) ou saisie du nom et de la liste INCI, corrigée ingrédient par ingrédient avant confirmation. **Le nom seul ne dit jamais la composition** : sans liste INCI, le produit est enregistré en « composition inconnue » et rien n'est déduit.
- **Reconnaissance** : correspondance exacte seulement (jamais par ressemblance de nom). Chaque alias porte sa provenance : `catalogue` (l'ingrédient figure dans l'INCI d'un produit de catalogue que la fiche relie à cet actif), `lexique` (lexique FR/EN du projet), `a_relire` (nom INCI exact, sans attestation dans les données du projet : relecture par un cosmétologue requise). Un ingrédient absent reste « non reconnu » : aucune fonction, aucun risque, aucune efficacité ne lui est attribués.
- **Points d'attention** (chacun avec règle, source et niveau de validation, dans « Pourquoi ce message ? ») : R1 actif ciblé présent dans plusieurs produits (information neutre) ; R2 règle `strong_evening` (validée : un seul exfoliant ou rétinoïde par soir, comptée en produits) ; R3 protection solaire (seulement si la fiche d'un actif reconnu la demande et qu'aucun produit déclaré « Protection solaire » n'est placé le matin) ; R4 composition inconnue ou sans ingrédient reconnu (vérification impossible ou limitée) ; R5 vitamine C et rétinoïde au même moment (règle `à_valider` : « à valider », jamais une incompatibilité établie). Prudence : substances de la liste `EXCLUDED` (reconnues par nom INCI exact, message neutre : « DERMAI ne donne pas de conseil, demandez l'avis d'un professionnel »), et produit que l'utilisateur déclare l'avoir déjà irrité.
- **Fréquences** : seulement le repère de départ de la fiche d'UN actif ciblé validé, présenté comme « Repère DERMAI » et jamais comme instruction du fabricant. Plusieurs actifs, composition inconnue, fiche à valider : aucune fréquence, « consultez la notice ».

## Simulation cosmétique avant/après (développée, FERMÉE, jamais testée en réel)

## Page d'administration du fondateur (V1, lecture seule, privée)

Une page « Administration » réservée au fondateur : solde d'unités Perfect Corp, comptes, utilisation par fonction, coûts officiels annoncés, état de configuration des fonctionnalités, quotas configurés. Elle ne modifie rien, ne lance aucune analyse, n'affiche aucune donnée individuelle (des nombres seulement). Aucune migration appliquée (une proposition SQL de lecture est à relire, voir plus bas), aucune clé `service_role`, aucun appel payant.

### Accès
- `DERMAI_ADMIN_USER_IDS` (variable serveur, **à créer dans Vercel par le fondateur**, jamais commitée) : identifiants de comptes Supabase (UUID) séparés par des virgules (Supabase, Authentication, Users, colonne UID). Absente, vide, ou contenant UNE entrée qui n'est pas un UUID : personne n'y accède. **`*` n'a aucun effet** : il invalide la liste.
- Contrôle **côté serveur, à chaque requête** (`api/admin-stats.js`) : session Supabase vérifiée (même mécanisme que les autres fonctions), puis identifiant vérifié comparé à la liste. L'identifiant ne vient jamais du navigateur.
- **Tout refus renvoie la même réponse 404** (`Not found`, sans contenu) : jeton absent ou invalide, Supabase injoignable, compte non listé, liste absente. Seul un fondateur reconnu peut obtenir un 405 (méthode autre que GET) ou un 400 (section inconnue). Réponses `Cache-Control: private, no-store`, `Vary: Authorization`.
- L'entrée de menu « Administration » apparaît seulement si cette API a répondu « fondateur » (une requête d'accès par session) ; sinon la route tapée à la main affiche « Page introuvable ». Ce n'est PAS un contrôle d'accès : l'API refuse à elle seule.

### Données (six blocs, sections `?section=credit|usage|costs|features|quotas`, plus `access`)
- **Solde** : `GET /s2s/v1.0/client/credit` (lecture). Catégories telles que retournées ; total « Api » annoncé avec sa source (convention du code officiel : lots dont le type commence par « Api ») ; autres catégories jamais additionnées. **Historique de consommation (24 h, 7 j, 30 j) : « non disponible »** (la forme de la réponse de `/client/credit/history` est inconnue, il n'est pas appelé ; une consommation n'est jamais déduite des réservations de quota).
- **Coûts officiels** : `GET /s2s/v2.0/credit/feature-cost` (lecture, paginée par `page_size` et `starting_token`, 10 pages au plus). Rapprochement EXACT par identifiant technique (`/task/<fonction>` appelé par DERMAI) ; plusieurs lignes par fonction conservées, aucun coût unique par catégorie ; un coût sans correspondance est « non rapproché » ; un montant absent est « indisponible ».
- **Comptes** et **Utilisation par fonction** (section `usage`, V2) : NOMBRES agrégés lus en base par la fonction SQL `admin_overview`, appelée par l'API avec le jeton du fondateur (`server/admin-usage.js`, aucune clé `service_role`, aucun SQL côté serveur). Comptes : total, nouveaux, connectés (dernière connexion), actifs, retour à 7 jours, inactifs 30 jours, jamais utilisé. Utilisation : demandes sur 7 et 30 jours et comptes concernés pour l'analyse, la simulation, le maquillage et les cheveux (unités en plus), et nombre d'analyses enregistrées dans l'historique. Une « demande » est une réservation de quota (elle a atteint l'étape fournisseur, réussie ou non) : **ce n'est ni un coût confirmé ni un nombre de résultats**. Une fonction dont la table de quota n'existe pas affiche « Non mesurée », jamais zéro ; une valeur invalide affiche « Indisponible ». La réponse SQL est reconstruite champ par champ (nombres entiers positifs seulement) : aucun identifiant, e-mail ni champ inconnu ne passe. Mémorisée 60 s côté serveur, après le contrôle d'accès.
- **Fonctionnalités** : activation (variable, valeur réellement lue par le code), autorisation (Personne, Liste restreinte avec le NOMBRE de comptes, Tous les utilisateurs, Tous les comptes connectés pour l'analyse), prérequis (clé Perfect Corp, Supabase, fonction SQL). État : Fermée, Bloquée, ou « Configurée : disponibilité non vérifiée » (la fonction SQL de quota ne peut pas être vérifiée sans réserver un crédit). Jamais d'identifiant de compte.
- **Quotas** : limites CONFIGURÉES (pas la consommation), unité, fenêtre, variable et origine (variable, valeur par défaut du code, ou variable invalide ignorée). Cheveux en unités.
- Les lectures Perfect Corp sont mémorisées en mémoire du serveur (solde 60 s, coûts 10 min, erreurs 15 s), après le contrôle d'accès. Toute source en échec s'affiche « Indisponible » avec une cause courte, jamais zéro. Sources : scripts officiels de `YouCam-API/skills` (instantané du 2026-09-01) lus hors dépôt ; le README officiel décrit ces deux lectures comme gratuites ; **aucune n'a été exécutée en réel** (tests simulés).
